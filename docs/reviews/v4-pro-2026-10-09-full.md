## Ответ модели

## 1. Критично (баги, дыры в безопасности)

### 1.1. Отсутствие защиты от записи в служебные/защищённые файлы через `tools.py`
**Суть:** Инструменты `write_file` и `edit_file` в `tools.py` не проверяют `blacklist_paths` / `blacklist_files` из конфигурации. Агент может напрямую модифицировать `.git/config`, `config/config.yaml`, `config/prompts.yaml`, `.ai-out/**` и другие критичные файлы.
**Зачем:** Автономный агент без контроля может сломать собственную конфигурацию или репозиторий, нарушить работу приложения.
**Оценка:** S
**Пример:**
```python
# tools.py, tool_write_file
abs_path.parent.mkdir(parents=True, exist_ok=True)
abs_path.write_text(content, encoding="utf-8")
```
Должно быть: перед записью вызвать `_path_is_blacklisted(rel_path, cfg)` или аналогичную проверку. Аналогично для `edit_file`.

### 1.2. Недостаточная фильтрация секретов в инструментах чтения
**Суть:** `scanner._contains_secret` применяется только при сканировании проекта, но не в `tool_read_file`, `run_shell` (`cat`, `grep`) или `list_files` (не содержимое). Секреты (API-ключи, токены) могут попасть в контекст LLM.
**Зачем:** Утечка секретов в сторонний API (DeepSeek) — критичная проблема безопасности.
**Оценка:** S
**Пример:**
в `tool_read_file` после чтения текста следует вызвать `_contains_secret` и либо маскировать, либо блокировать вывод. Для `run_shell` можно добавить пост-фильтрацию stdout/stderr.

### 1.3. `shell=True` в `run_verify_commands`
**Суть:** Функция `run_verify_commands()` в `apply.py` использует `subprocess.run(cmd, shell=True, ...)`. Если конфиг `verify_commands` или CLI-аргумент `--verify-commands` окажется под контролем LLM (через изменение конфига через агента, хотя blacklist это запрещает, но возможны обходы), это открывает инъекцию произвольных команд.
**Зачем:** Устранение вектора RCE.
**Оценка:** M
**Пример:**
```python
proc = subprocess.run(cmd, shell=True, cwd=root, ...)
```
Заменить на `shlex.split(cmd)` и `shell=False`.

### 1.4. Возможность деструктивных действий через `run_shell`
**Суть:** Whitelist команд в `tools.py` не ограничивает аргументы. Например, `find . -delete`, `git clean -fd` (запрещён `clean`, но можно `git branch -D` — запрещён), `python -m pytest --pdb` (может дать интерактивный shell?). Также `cat` может вывести бинарные/большие файлы, `grep` — утечка секретов.
**Зачем:** Агент может случайно или намеренно удалить файлы, привести проект в неработоспособное состояние.
**Оценка:** M
**Пример:**
Добавить чёрный список опасных флагов для разрешённых команд (например, `find` без `-delete`, `-exec`; `git` с ограниченными подкомандами и т.п.). Либо использовать `--` и проверять, что команда не содержит опасных опций.

### 1.5. Неатомарное применение плана с внешними эффектами
**Суть:** В `apply_plan` операции записываются последовательно. Если план содержит `create_file`, который создаёт файл, а затем следующая операция падает, откатываются только файлы, созданные в `backups_made`. Однако если операция вызывает создание каталога и затем файла, откат удалит только созданный файл, но каталог останется (пустой). Также возможны побочные эффекты от частично выполненного JSON (например, `edit_file` меняет один файл, потом ошибка — откатывается). Это приемлемо, но может оставить временные артефакты.
**Зачем:** Для полной автономности нужна транзакционность или гарантированный откат без следов.
**Оценка:** L
**Рекомендация:** Использовать `backup_dir` для создания полной копии затрагиваемых файлов и каталогов перед применением, а также вести журнал созданных каталогов для их удаления при откате.

## 2. Архитектура и структура

### 2.1. Разделение слоёв: смешивание бизнес-логики и инфраструктуры в `actions.py`
**Суть:** `run_action` отвечает за сканирование, кэш, запрос к LLM, расчёт стоимости, запись usage и сохранение отчёта. Это нарушает Single Responsibility, усложняет тестирование.
**Зачем:** Для поддержки автономности нужны изолированные компоненты, которые можно мокать и переиспользовать.
**Оценка:** M
**Пример кода:**
```python
# actions.py, run_action
cost = calculate_cost(...)
append_usage(...)
cache_mod.save(...)
return ActionResult(...)
```
Вынести работу с usage и кэшем в отдельные сервисы (например, `UsageService`, `CacheService`), а `run_action` сделать тонким координатором.

### 2.2. Отсутствие абстракции для LLM-клиента
**Суть:** `LLMClient` напрямую использует `OpenAI` SDK, без интерфейса. Нельзя подменить на мок в тестах или в dry-run режиме.
**Зачем:** Для тестирования и возможности переключения провайдера.
**Оценка:** M
**Рекомендация:** Определить протокол `LLMClientProtocol` с методом `chat()`, реализовать `OpenAIClient` и `MockLLMClient`.

### 2.3. Запутанная логика в `agent.py` (декомпозиция, replan, tool loop)
**Суть:** Модуль `agent.py` содержит множество разнородных функций: парсинг планов, запросы к LLM, управление подзадачами, replan, журналирование. Субъективно сложно поддерживать.
**Зачем:** Разделение на отдельные классы/модули (`planner.py`, `decomposer.py`, `tool_loop.py`) улучшит читаемость и тестируемость.
**Оценка:** L
**Пример:**
Вынести `parse_agent_plan`, `parse_decompose_response`, `_is_diagnostic_step` и т.п. в отдельные модули.

### 2.4. Конфигурация `AppConfig` содержит слишком много несвязанных секций
**Суть:** `AppConfig` объединяет `api`, `currency`, `scanning`, `output`, `usage`, `write`, `fix`, `git`, `agent`, `actions`. Это гигантский объект, который пробрасывается во все функции.
**Зачем:** Упростить внедрение зависимостей, уменьшить связность.
**Оценка:** L
**Рекомендация:** Передавать только нужные секции конфига в функции (например, `run_action` не нужен `usage`), либо использовать Deps-контейнер.

### 2.5. Дублирование логики валидации в `apply.py` и `tools.py`
**Суть:** `validate_operations` в `apply.py` проверяет blacklist, уникальность `old`, существование файлов для `edit_file`, а `tool_edit_file` в `tools.py` имеет похожую, но не идентичную логику (не проверяет blacklist, но проверяет уникальность).
**Зачем:** Избежать расхождений в поведении между планом (пакетный режим) и агентом (интерактивный tool loop).
**Оценка:** M
**Рекомендация:** Создать общий модуль `validation.py`, который используется обеими частями.

## 3. Читаемость и поддерживаемость

### 3.1. Непоследовательные имена: `run_action`, `run_agent`, `run_tool_loop`
**Суть:** Разные префиксы и стили (`run_action`, `run_agent`, `run_planner_decompose`, `run_agent_decompose`).
**Зачем:** Единый стиль (например, `execute_*`) упрощает навигацию.
**Оценка:** S
**Пример:**
`run_action` → `execute_action`, `run_agent` → `execute_agent`, `run_tool_loop` → `execute_tool_loop`.

### 3.2. Длинные функции (например, `run_action`, `run_fix_action`, `apply_plan`)
**Суть:** `run_action` содержит более 150 строк с вложенными условиями и кэшем. Трудно читать и менять.
**Зачем:** Улучшение поддерживаемости.
**Оценка:** M
**Рекомендация:** Разбить на приватные методы: `_scan`, `_render_prompt`, `_check_cache`, `_call_llm`, `_save_results`.

### 3.3. Комментарии на русском и английском вперемешку, не всегда отражают актуальное поведение
**Суть:** Часть комментариев устарела (например, в `run_action` упоминание "review 3.2" без контекста).
**Зачем:** Поддержание актуальности документации.
**Оценка:** S
**Рекомендация:** Пройтись по коду и обновить/удалить устаревшие комментарии; договориться о едином языке (например, русский для пояснений).

### 3.4. Большое количество магических строк и чисел
**Суть:** Примеры: `"edit"`, `"write"`, `"finish"`, размеры буферов (20000, 50000, 10000) разбросаны по коду.
**Зачем:** Централизовать константы для удобства изменений.
**Оценка:** S
**Рекомендация:** Создать `constants.py` или использовать перечисления.

## 4. Тесты

### 4.1. Отсутствие модульных тестов для критических компонентов
**Суть:** В проекте нет видимых тестов (tree не показывает `tests/`). Нет тестов для `apply.py`, `scanner.py`, `tools.py`, `cache.py`.
**Зачем:** Без тестов рефакторинг и расширение автономности рискованны.
**Оценка:** L
**Рекомендация:** Начать с тестов на `apply.parse_response`, `apply.validate_operations`, `scanner.scan_project`, `tools._validate_command`, `cache.compute_hash`.

### 4.2. Тесты для LLM-интеграций с использованием моков
**Суть:** Нет мок-объектов для LLMClient и внешних HTTP (pricing, git).
**Зачем:** Изолировать тесты от внешних зависимостей.
**Оценка:** M
**Пример:** Создать `FakeLLMClient`, который возвращает предопределённые `LLMResponse` для проверки логики `run_action` и `run_fix_action` без реальных запросов.

### 4.3. Тесты безопасности: проверка путей, blacklist, shell-whitelist
**Суть:** Необходимы тесты, что `_safe_path` запрещает выход за root, `tool_edit_file` не изменяет файлы из blacklist, `_validate_command` отклоняет `;`, `|`, `$`, опасные подкоманды.
**Зачем:** Критично для автономного агента.
**Оценка:** M
**Рекомендация:** Параметризованные тесты на каждый случай.

### 4.4. Интеграционные тесты с реальным проектом
**Суть:** Проверка apply_plan на простом фиктивном проекте: применение корректного плана, откат при ошибке, проверка сохранения бэкапов.
**Зачем:** Гарантировать работоспособность механизма изменений.
**Оценка:** L
**Пример:** Создать временный каталог, сгенерировать файлы, применить план, проверить содержимое, затем откатить и убедиться в восстановлении.

## 5. Производительность

### 5.1. Неоптимальное сканирование: повторное чтение файлов и директорий
**Суть:** `scan_project` сначала обходит дерево, собирает кандидатов, затем сортирует и читает файлы. Для больших проектов это двойной проход.
**Зачем:** Сократить время сканирования.
**Оценка:** M
**Рекомендация:** Объединить сбор и чтение в один проход, но с учётом приоритизации (может потребоваться буферизация списка файлов с их размером, но без повторного `stat`).

### 5.2. Оценка токенов `_estimate_tokens` грубая (3 символа/токен)
**Суть:** Используется для бюджетирования. Реальное потребление может отличаться в разы.
**Зачем:** Точнее управлять бюджетом контекста.
**Оценка:** S
**Рекомендация:** Использовать более точную оценку (например, `tiktoken` для Python/JSON), либо калиброваться по реальному использованию.

### 5.3. Неэффективное обновление usage summary
**Суть:** `append_usage` пишет только JSONL; summary пересчитывается отдельной командой `usage`, что может быть медленным при большом `usage.jsonl`.
**Зачем:** Ускорить получение сводки.
**Оценка:** M
**Рекомендация:** Использовать базу данных (SQLite) для хранения usage, или обновлять summary инкрементально при каждой записи (возможно с дебаунсом).

### 5.4. Кэш отчётов: полное копирование содержимого файлов в хэш
**Суть:** `compute_hash` хэширует весь `scan.files`, включая все содержимое файлов. Для больших проектов это может быть медленным.
**Зачем:** Ускорить проверку кэша.
**Оценка:** M
**Рекомендация:** Использовать хэши путей файлов и их mtime/size, а не содержимого, либо комбинировать (быстрый хэш на основе mtime + size, затем полный хэш при несовпадении). Но тогда возможны ложные попадания. Альтернатива — хранить хэш от дерева файлов и содержимого, но вычислять интенсивно.

### 5.5. Параллельное выполнение независимых подзадач в декомпозиции
**Суть:** В `run_agent_decompose` подзадачи выполняются последовательно. Если подзадачи независимы, их можно запускать параллельно, сокращая общее время.
**Зачем:** Ускорить работу агента.
**Оценка:** L (сложная реализация из-за общих файлов и конфликтов)
**Рекомендация:** Реализовать опциональный параллельный режим с блокировками на уровне файлов или ветками git для каждой подзадачи.

## 6. Инструменты и CI

### 6.1. Отсутствие настроенного линтера и форматтера
**Суть:** В проекте нет конфигурации `ruff`, `black` или `mypy`.
**Зачем:** Поддержание качества кода.
**Оценка:** S
**Рекомендация:** Добавить `pyproject.toml` с настройками `ruff`, `black`, `mypy`, запускать в CI.

### 6.2. Нет автоматического запуска тестов и сборки
**Суть:** Отсутствует CI файл (GitHub Actions, GitLab CI).
**Зачем:** Проверять каждый MR/PR.
**Оценка:** M
**Рекомендация:** Создать `.github/workflows/ci.yml` с шагами: установка зависимостей, линтер, тесты, type-check.

### 6.3. Управление зависимостями не формализовано
**Суть:** В дереве файлов нет `requirements.txt` или `pyproject.toml` с зависимостями.
**Зачем:** Воспроизводимость окружения.
**Оценка:** S
**Рекомендация:** Добавить `pyproject.toml` с зависимостями (`typer`, `rich`, `pydantic`, `openai`, `pathspec`, `httpx`, `pytest` для dev) и использовать `poetry` или `pip-tools`.

### 6.4. Не настроено автотестирование безопасности (SAST)
**Суть:** Отсутствует анализ на уязвимости (bandit, semgrep).
**Зачем:** Поймать паттерны вроде `shell=True` автоматически.
**Оценка:** M
**Рекомендация:** Интегрировать `bandit` в CI.

### 6.5. Отсутствие метрик и алертов для агента
**Суть:** В автономном режиме важно отслеживать успешность, стоимость, ошибки. Есть usage.jsonl, но нет визуализации или алертов.
**Зачем:** Оперативный мониторинг.
**Оценка:** L
**Рекомендация:** Добавить экспорт метрик в Prometheus/InfluxDB или простой скрипт аналитики.

## Приоритизация для полной автономности

1. **Критичные безопасность:** файловые ограничения, секреты, shell-инъекции — без них агент опасен.
2. **Надёжность:** тесты для apply_plan, tools, rollback; транзакционность.
3. **Модульность:** выделение сервисов (usage, cache, llm) для тестируемости.
4. **Улучшение планирования:** усиление `phase1` (релевантные файлы), возможность отката подзадачи.
5. **Мониторинг и CI:** после стабилизации ядра.

Реализация этих пунктов позволит агенту безопасно работать без человека, сохраняя код и данные в целостности.
