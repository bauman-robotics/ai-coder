## Анализ проекта ai_coder после split-file 10.65

### Общие впечатления

Разбиение `agent.py` на 9 модулей снизило размер отдельных файлов и упростило навигацию. Однако границы модулей проведены не всегда удачно: есть циклические зависимости, дублирование логики, размытая ответственность. Сохранение обратной совместимости через `agent/__init__.py` с ручным перечислением `__all__` хрупко. Ниже – конкретные проблемы и приоритетные доработки.

## 1. Критично (баги, дыры в безопасности)

### 1.1. Опасные команды в `apply.run_verify_commands`
**Суть:**
В `run_verify_commands` чёрный список `_VERIFY_FORBIDDEN_COMMANDS` проверяет только первый токен. Команда `python` разрешена, хотя через `python -c` можно выполнить произвольный код. Аналогично `git` не запрещён, но в этом контексте не используется.
**Пример:**
```python
if tokens[0] in _VERIFY_FORBIDDEN_COMMANDS:
    errors.append(...)
```
Если `verify_commands` содержит `python -c 'import os; os.system("rm -rf /")'`, это будет выполнено без предупреждения.
**Зачем:**
Устранить риск запуска деструктивных операций при случайной или злонамеренной генерации команд.
**Трудозатраты:** S

### 1.2. Откат созданных директорий при ошибке в `apply_plan`
**Суть:**
В `apply_plan` при исключении внутри цикла происходит восстановление файлов и удаление созданных файлов, но не удаляются пустые директории, созданные операциями `create_file`.
**Пример:**
```python
new_dirs = _collect_new_dirs(abs_path.parent, root)
...
# при ошибке:
for abs_path in created_files:
    abs_path.unlink()
# директории остаются
```
Это приводит к мусорным пустым каталогам после неудачного применения.
**Зачем:**
Гарантировать полный откат – состояние проекта должно быть точно таким же, как до начала применения.
**Трудозатраты:** S

### 1.3. Отсутствие проверки `llm=None` при кэш-хите phase1
**Суть:**
`run_planner_phase1` возвращает `PlannerPhase1Result` с `llm=None`, если использован кэш. Потребители могут обращаться к `phase1_result.llm` без проверки.
**Пример:**
В `run_agent` (показан фрагмент) `phase1_result` используется только для `target_files`, но в других местах (например, в отчётах) может ожидаться `llm`.
**Зачем:**
Предотвратить `AttributeError` при первом же кэш-попадании.
**Трудозатраты:** S

### 1.4. Подозрительная логика в `tool_loop._handle_finish`
**Суть:**
Условие `if ctx.success and action.tool not in ("read_file", "read_symbol", "list_files")` бессмысленно: если `action.finish` истинно, то `action.tool` скорее всего `"finish"`, а не read-инструмент. Этот код не вредит, но указывает на недопонимание логики.
**Пример:**
```python
if ctx.success and action.tool not in (...):
    write_attempts = ...
```
Вероятно, задумывалось что-то другое, но текущая проверка всегда выполняется для обычного `finish`.
**Зачем:**
Упростить и сделать код предсказуемым.
**Трудозатраты:** S

### 1.5. Ненадёжный парсер markdown-обёртки в `parse_response`
**Суть:**
Код снимает обёртку ` ``` `, предполагая, что первая и последняя строки – это маркеры. Если внутри JSON-строк есть ` ``` `, парсер может удалить лишнее.
**Пример:**
```python
if text.startswith("```"):
    lines = text.splitlines()
    lines = lines[1:]
    if lines and lines[-1].strip().startswith("```"):
        lines = lines[:-1]
```
Лучше искать первую `{` и последнюю `}` через регулярное выражение, не полагаясь на структуру строк.
**Зачем:**
Устойчивость к реальным ответам LLM.
**Трудозатраты:** S

## 2. Архитектура и структура

### 2.1. Дублирование логики запросов к LLM, расчёта стоимости и учёта
**Суть:**
Функции в `planner.py`, `classic.py`, `decomposer.py`, `autofix.py`, `tool_loop.py` повторяют один и тот же шаблон:
1. Получить `is_peak`, `cny_to_rub`, `usd_to_rub`.
2. Создать `LLMClient`.
3. Вызвать `client.chat(...)`.
4. Рассчитать стоимость через `calculate_cost`.
5. Вызвать `append_usage`.
Это разбросано по ~10 местам.
**Зачем:**
Централизовать работу с LLM → меньше кода, единообразная обработка ошибок, проще добавлять новые модели.
**Трудозатраты:** M

### 2.2. Локальные импорты внутри функций для избежания циклов
**Суть:**
В `classic._run_agent_step` встречается:
```python
from ..actions import run_fix_action
from ..apply import rollback as do_rollback
```
Это симптом циклической зависимости на уровне пакетов.
**Зачем:**
Устранить циклические импорты, выделив `run_fix_action` в модуль, не зависящий от `agent`, или передавать как dependency.
**Трудозатраты:** M

### 2.3. Размытая ответственность `planner.py`
**Суть:**
В `planner.py` собраны и парсеры JSON (`parse_agent_plan`, `parse_decompose_response`, ...), и функции запросов к LLM (`run_planner`, `run_planner_phase1`, `run_planner_decompose`, `run_planner_replan`), и утилиты для slug, кэша, оценки стоимости.
**Зачем:**
Разделить на `planner.py` (запросы) и `parsers.py` (парсеры) для лучшей читаемости и тестируемости.
**Трудозатраты:** S

### 2.4. Ручное перечисление `__all__` в `agent/__init__.py`
**Суть:**
Список экспортируемых имён собран вручную из `__all__` каждого модуля плюс дополнительные имена. При добавлении нового публичного имени в модуль легко забыть обновить `__init__.py`.
**Пример:**
```python
__all__ = list(_models_all) + ... + ["WritePlan", ...]
```
**Зачем:**
Использовать динамическое объединение `__all__` через импорт звёздочкой или автоматическое сканирование модулей.
**Трудозатраты:** S

### 2.5. Огромный `tool_loop.py`
**Суть:**
Модуль `tool_loop.py` содержит более 31k символов: контекст, итерацию, обработку finish, сохранение журнала, загрузку истории, бэкап, парсинг. Это кандидат на дальнейшее разбиение.
**Зачем:**
Упростить поддержку, выделив классы `ToolLoopSession`, `Journal`, `BackupManager`.
**Трудозатраты:** L

## 5. Производительность

### 5.1. Кэширование результатов сканирования проекта
**Суть:**
`scan_project_metadata` вызывается в начале каждого `run_tool_loop`, `run_planner_phase1`, `run_split_goals`, хотя структура проекта между итерациями может не меняться.
**Зачем:**
Снизить накладные расходы на обход файловой системы.
**Трудозатраты:** S

### 5.2. Оптимизация `tool_read_symbol` для больших проектов
**Суть:**
Используется `project_root.rglob("*.py")` при каждом вызове `read_symbol` без указания пути. Для проектов с тысячами файлов это дорого.
**Зачем:**
Кэшировать список Python-файлов или построить индекс имён.
**Трудозатраты:** S

### 5.3. Однократное чтение файлов в `apply_plan`
**Суть:**
При нескольких операциях `edit_file` над одним файлом, файл читается заново для каждой операции.
**Зачем:**
Читать файл один раз, применять все правки к копии, затем записывать.
**Трудозатраты:** S

### 5.4. Улучшить оценку токенов в `_estimate_next_cost_rub`
**Суть:**
Грубая оценка `len(text)//3` может приводить к слишком консервативной остановке бюджета, особенно при длинных промптах.
**Зачем:**
Использовать более точную оценку (например, учитывать tokenizer модели) или проводить post-проверку после первого запроса.
**Трудозатраты:** S
