## 1. Критично (баги, дыры в безопасности)

### 1.1. Кэш не учитывает `write.*` конфиг и возвращает не перепроверенный `WritePlan`

- **Суть:**  
  В `ai_coder/actions.py` ключ кэша строится через `cache_mod.compute_hash(...)` только из:
  - содержимого файлов `scan.files`,
  - шаблонов `prompt_system` / `prompt_user`,
  - `model`, `depth`.

  При этом `cfg.write.blacklist_paths`, `cfg.write.blacklist_files`, `cfg.write.max_operations`, `cfg.output.use_cache` и другие параметры безопасности не попадают в хэш.

  В `actions.run_action` при попадании в кэш:
  ```python
  if cached is not None:
      llm_resp, cached_plan = cached
      ...
      return ActionResult(
          ...
          write_plan=cached_plan,
          from_cache=True,
      )
  ```
  `cached_plan` отдаётся как есть, **без повторной валидации** `build_plan(...)` / `validate_operations(...)`.

- **Зачем:**  
  Сценарий:
  1. Вчера план для `write_readme` изменял `pyproject.toml`, и это было разрешено.
  2. Сегодня пользователь добавил `pyproject.toml` в `write.blacklist_files`.
  3. Старый кэш всё ещё валиден по текущему хэшу, `plan.valid == True`, и CLI `run --apply` применит правку в запрещённый файл.

  Аналогичная проблема в `run_fix_action`: fix-план из кэша тоже не перепроверяется через `validate_operations`.

- **Оценка:** `S`

### 1.2. `pricing.get_rate()` падает, если `.ai-out/rates_cache.json` нельзя записать

- **Суть:**  
  В `pricing.py`:
  ```python
  _save_cache(root, cache)
  ```
  вызывается после успешного `fetch_cbr_rates()` без перехвата `OSError`.  
  Если корневая директория проекта или `.ai-out` не writable, исключение пробрасывается наверх и ломает весь запуск, хотя курс получен и стоимость могла бы быть рассчитана.

- **Зачем:**  
  AI-инструмент часто запускается на чужих репозиториях, в том числе внутри контейнеров или read-only монтированиях. Падение из-за записи необязательного кэша – плохой UX и баг.

- **Оценка:** `S`

### 1.3. `usage.py` игнорирует `UsageConfig.jsonl/summary` и пересчитывает summary на каждый запрос

- **Суть:**  
  В `usage.append_usage`:
  ```python
  global_jsonl = output_root / "usage.jsonl"
  ...
  _rebuild_summary(global_jsonl, output_root / "usage_summary.json")
  ```
  Поля `usage_cfg.jsonl` и `usage_cfg.summary` из `config.yaml` вообще не используются.  
  Плюс `_rebuild_summary()` читает **весь** JSONL и перезаписывает summary при каждом вызове `append_usage`.

- **Зачем:**  
  Это одновременно:
  - конфигурационная ошибка: пользователь меняет путь в `config.yaml`, а реально пишутся пути по умолчанию;
  - производительность: `N` запросов дают `O(N²)` по вводу-выводу. Для агента с шагами/fix-итерациями быстро становится заметно.

- **Оценка:** `M`

### 1.4. Нет контентной фильтрации секретов перед отправкой в LLM

- **Суть:**  
  `scanner.py` фильтрует только по именам файлов:
  ```python
  secret_ignore:
    - "*.env"
    - ".env*"
    - "*secret*"
    - "*credential*"
    - "*password*"
    - "*.pem"
    - "*.key"
  ```
  Содержимое файлов не анализируется. Если в `settings.py` есть:
  ```python
  API_TOKEN = "sk-..."
  DB_PASSWORD = "super_secret"
  ```
  оно уходит в DeepSeek.

- **Зачем:**  
  Инструмент отправляет весь проект во внешний API. Нужно либо вырезать/редактировать найденные секреты перед рендером промпта, либо явно блокировать отправку. Это прямое снижение риска утечки.

- **Оценка:** `M`–`L`

## 2. Архитектура и структура

### 2.1. Дублирование LLM-пайплайна в `run_action` и `run_fix_action`

- **Суть:**  
  В `actions.py` почти одинаковые блоки:
  - `scan_project`
  - загрузка `prompt_entry`
  - `get_rate`, `is_peak_now`
  - `LLMClient.chat`
  - `build_plan`
  - `calculate_cost`
  - `append_usage`
  - `cache.save`

  Разница только в промпте, хэше и имени действия. Поддерживать два параллельных блока уже привело к рассинхрону поведения.

- **Зачем:**  
  Вынести общий метод, например:
  ```python
  def _execute_llm_action(
      *,
      action_name,
      prompt_entry,
      render_extra,
      project_root,
      cfg,
      prompts_cfg,
      model,
      depth,
      ...
  ) -> tuple[LLMResponse, WritePlan | None, CostBreakdown]
  ```
  Кэш-ключ тоже должен вычисляться по одному месту.

- **Оценка:** `M`

### 2.2. Локальные импорты внутри `_run_agent_step`

- **Суть:**  
  В `ai_coder/agent.py`:
  ```python
  from .apply import build_plan, apply_plan, check_python_files, rollback as do_rollback
  from .actions import run_fix_action
  ```
  находятся внутри функции. Это прячет зависимости и мешает DI/тестированию.

- **Зачем:**  
  Лучше:
  - импортировать на уровне модуля `apply` без цикла;
  - `run_fix_action` передавать как параметр-фабрику или вынести fix-цикл в отдельный сервис, чтобы `agent.py` не зависел от CLI-ориентированного модуля `actions`.

- **Оценка:** `S`

### 2.3. Дублирование извлечения JSON-объекта

- **Суть:**  
  `apply.parse_response` и `agent.parse_agent_plan` оба реализуют:
  - снятие markdown-обёртки ` ```json ... ``` `;
  - поиск первого `{` и последнего `}`;
  - `json.loads`.

- **Зачем:**  
  Вынести в `ai_coder/json_utils.py`:
  ```python
  def extract_json_object(content: str) -> tuple[str | None, str | None]:
      ...
  ```
  Это упростит поддержку и добавит единый тест на толерантный парсинг.

- **Оценка:** `S`

### 2.4. CLI-слой `run` содержит бизнес-логику применения и fix-циклов

- **Суть:**  
  `cli.run` сейчас сам решает:
  - подтверждение `--apply --yes`,
  - создание бэкапов,
  - цикл авто-исправлений,
  - откат,
  - сводку.

  Это ~100+ строк логики прямо в функции Typer.

- **Зачем:**  
  Логику надо перенести в отдельный `runner.py`, чтобы:
  - тестировать без Typer;
  - переиспользовать из агента;
  - уменьшить связность CLI/бизнес-правил.

- **Оценка:** `L`

### 2.5. Мёртвые поля конфигурации

- **Суть:**  
  Не используются:
  - `UsageConfig.jsonl`
  - `UsageConfig.summary`
  - `AgentConfig.verify_commands`
  - `AgentConfig.include_read_steps`

  В `cache.save` есть параметр `report_path`, который сохраняется в JSON кэша, но нигде не читается.

- **Зачем:**  
  Это создаёт ложное впечатление реализованных фич. Либо задействовать, либо удалить. Для `agent` это особенно важно: `verify_commands` и `include_read_steps` заявлены, но молча игнорируются.

- **Оценка:** `S`

## 3. Читаемость и поддерживаемость

### 3.1. Широкое использование нетипизированных `cfg`

- **Суть:**  
  Например:
  ```python
  def validate_operations(plan: WritePlan, project_root: Path, cfg) -> None:
  ```
  ```python
  def get_rate(root: Path, currency_cfg, *, key: str) -> Rate:
  ```
  ```python
  def is_peak_now(schedule) -> tuple[bool, str | None]:
  ```

- **Зачем:**  
  Указать `cfg: AppConfig`, `currency_cfg: CurrencyPair`, `schedule: PeakSchedule`. Это заметно улучшит навигацию и позволит включить более строгий `mypy`.

- **Оценка:** `S`

### 3.2. Неочевидный cache key в `run_fix_action`

- **Суть:**  
  В `actions.run_fix_action`:
  ```python
  hash_hex = cache_mod.compute_hash(
      scan=scan,
      prompt_system=prompt_entry.system + "\nERRORS:\n" + errors_text + "\nPREV:\n" + previous_plan_text,
      prompt_user=prompt_entry.user,
      model=model,
      depth=depth,
  )
  ```
  При этом реальный промпт рендерится через `render_prompt(..., extra={...})`.

- **Зачем:**  
  Хэш считается по «синтетическому» system, а не по финальному промпту. Это хрупко: изменится `prompts.fix_errors_json.user`, и ключ может не учесть часть переменных. Лучше рендерить сначала, а хэшировать уже готовые `system` и `user`.

- **Оценка:** `S`

### 3.3. `StepResult.write_plan` и часть параметров нетипизированы

- **Суть:**  
  В `agent.py`:
  ```python
  write_plan: object | None
  ```
  В `output.py` и `cli.py`:
  ```python
  def _render_write_section(plan) -> str: ...
  def _print_plan_summary(plan) -> None: ...
  ```

- **Зачем:**  
  Использовать `WritePlan` напрямую или `TYPE_CHECKING`. Сейчас легко передать не тот объект.

- **Оценка:** `S`

### 3.4. Магические строки `.ai-out`, `usage.jsonl`, `usage_summary.json`

- **Суть:**  
  Эти строки зашиты в `pricing`, `usage`, `apply`, `cli`. Если пользователь изменит `output.dir`, часть подсистем всё равно будет писать в `.ai-out`.

- **Зачем:**  
  Создать константы и/или прокидывать путь единообразно.

- **Оценка:** `S`

## 5. Производительность

### 5.1. `_rebuild_summary` вызывается на каждый `append_usage`

- **Суть:**  
  Уже упомянуто в 1.3.  
  ```python
  with jsonl_path.open(...) as f:
      for line in f:
          ...
  ```
  На 1000 строк JSONL и 1000 вызовах получаем миллионы операций чтения.

- **Зачем:**  
  Варианты:
  - инкрементально обновлять summary;
  - пересчитывать summary только в конце `run`;
  - использовать отдельную команду `ai-coder usage summary`.

- **Оценка:** `M`

### 5.2. `_load_specs_recursive` обходит служебные каталоги

- **Суть:**  
  В `scanner.py`:
  ```python
  for gi in sorted(root.rglob(".gitignore")):
  ```
  Этот `rglob` проходит через `.venv`, `node_modules`, `.git`, `__pycache__` и т.д., хотя они всё равно исключаются из сканирования позднее.

- **Зачем:**  
  В монорепозиториях или Python-проектах с виртуальным окружением это может занять секунды и открыть неожиданные `.gitignore` из зависимостей.

  Лучше использовать `os.walk` с `dirnames` pruning или сначала получить все `.gitignore`, не заходя в `_SERVICE_DIRS`.

- **Оценка:** `M`

### 5.3. `_match_any` на каждый файл компилирует `PathSpec` ✅ ИСПРАВЛЕНО (6.8)

- **Суть:**  
  В `scanner.py`:
  ```python
  def _match_any(path_posix: str, patterns: list[str]) -> bool:
      if not patterns:
          return False
      spec = pathspec.PathSpec.from_lines("gitignore", patterns)
      return spec.match_file(path_posix) or spec.match_file(path_posix + "/")
  ```
  Для каждого файла/директории создаётся новый `PathSpec`.

- **Зачем:**  
  Достаточно один раз создать:
  ```python
  extra_spec = pathspec.PathSpec.from_lines("gitignore", extra_patterns)
  secret_spec = pathspec.PathSpec.from_lines("gitignore", secret_patterns)
  ```
  и передавать их в обход.

- **Оценка:** `S`

### 5.4. Пересканирование проекта на каждой fix-итерации

- **Суть:**  
  `run_fix_action` и агент на каждой итерации `scan_project` заново. Для маленьких проектов незаметно, для больших — дорого.

- **Зачем:**  
  Это отчасти оправдано: файлы меняются после `apply`. Но можно:
  - после первичного скана кэшировать дерево/размеры;
  - сканировать только изменённые файлы.

- **Оценка:** `M`

## 6. Инструменты и CI

### 6.1. Нет CI pipeline

- **Суть:**  
  В проекте нет `.github/workflows` / GitLab CI.

- **Зачем:**  
  Добавить минимальный пайплайн:
  ```yaml
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with:
        python-version: ["3.10", "3.11", "3.12"]
    - run: pip install -e ".[dev]"
    - run: ruff check .
    - run: mypy ai_coder
    - run: pytest --cov=ai_coder --cov-fail-under=60
  ```
  Это сразу ловит регрессии из-за изменений типов, неиспользуемых импортов и т.п.

- **Оценка:** `M`

### 6.2. Нет pre-commit hooks

- **Суть:**  
  `ruff` и `mypy` есть в dev-зависимостях, но не запускаются автоматически перед коммитом.

- **Зачем:**  
  Добавить `.pre-commit-config.yaml`:
  - `ruff`
  - `mypy ai_coder`
  - `check-yaml`
  - `end-of-file-fixer`

- **Оценка:** `S`

### 6.3. `mypy` не сконфигурирован

- **Суть:**  
  В `pyproject.toml` нет секции `[tool.mypy]`. С учётом нетипизированных `cfg` и `plan` он не запускается полноценно.

- **Зачем:**  
  Добавить:
  ```toml
  [tool.mypy]
  python_version = "3.10"
  strict = true
  [[tool.mypy.overrides]]
  module = ["tests.*"]
  disallow_untyped_defs = false
  ```
  Придётся сначала дописать типы, указанные в разделе «Читаемость».

- **Оценка:** `M`

### 6.4. Ruff сконфигурирован поверхностно

- **Суть:**  
  В `pyproject.toml`:
  ```toml
  [tool.ruff]
  line-length = 100
  target-version = "py310"
  ```
  Нет `select`, `ignore`, `isort`-совместимых правил.

- **Зачем:**  
  Включить правила:
  ```toml
  select = ["E", "F", "I", "UP", "B", "SIM"]
  ```
  Это автоматически поднимет качество: порядок импортов, упрощения, потенциальные баги.

- **Оценка:** `S`

### 6.5. Нет `py.typed` и LICENSE

- **Суть:**  
  README сам указывает: лицензии нет, поле `license` в `pyproject.toml` отсутствует. Также нет `ai_coder/py.typed`.

- **Зачем:**  
  Если пакет решат использовать как библиотеку, отсутствие `py.typed` не даст типов. Лицензия важна для распространения.

- **Оценка:** `S`

### 6.6. Не зафиксированы точные версии зависимостей

- **Суть:**  
  `requirements.txt` и `pyproject.toml` используют только минимальные версии:
  ```
  typer>=0.12
  ...
  ```
  Lock-файла нет.

- **Зачем:**  
  Для воспроизводимости CI и пользовательских установок добавить `uv.lock` или `requirements.lock`.

- **Оценка:** `S`
