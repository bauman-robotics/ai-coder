# Автономность: принципы и план

Документ описывает, **что такое автономность** в `ai-coder`, что
**уже работает**, что **мешает**, и **план** движения к полной
автономности. Связан с `docs/roadmap.md`, `docs/experiments.md`,
`TODO.md`.

**Дата создания:** 2026-10-10
**Статус:** активный план, Этап 1 (E8)

---

## 1. Что такое автономность

**Наивное определение:** «модель справляется с первого раза» — это
**качество модели**, а не автономность.

**Настоящее определение:** агент **сам** понимает провал, **сам**
перепланирует, **сам** доводит до результата. Модель может быть
**слабой** — автономность **компенсирует**.

**Четыре уровня (+ 2.5):**

| Уровень | Что | Когда работает | Флаг |
|---|---|---|---|
| 1 | Одна попытка | Простые задачи | `--tool-loop` |
| 2 | Провалился → fix → успех | Verify упал | `--auto-fix-issues` |
| **2.5** | **Reverse-check** — LLM перечитывает свой diff | Всегда (опц.) | `--reverse-check` ✅ |
| 3 | Декомпозиция + replan | Многошаговые задачи | `--decompose-replan` |
| 4 (цель) | Рекурсивный replan | Сложные задачи | *не реализовано* |

**Уровни 1-3 — есть.** **Уровень 2.5 — есть (10.45).** **Уровень 4 — цель.**

**Уровень 2.5 — reverse-check:** ✅ **ЗАКРЫТО 10.45** (см. E20/E23).
После `finish(success)` LLM **перечитывает** свой diff и отвечает:

- «Соответствует ли diff goal?»
- «Нет ли семантических ошибок?»

**Зачем:** ловит ошибки, которые **verify не видит**. Пример:
агент исправил `return a - b` → `return a + b`, тесты зелёные,
**но** задача была «сделать sub, не add» — LLM **перечитала diff**
и заметила.

**Оценка:** ~4 ч.

## 2. Что уже работает

**Фундамент автономности:**

- **Tool loop** (9.1-9.4) — модель сама вызывает инструменты.
- **Retry при `missing args`** (10.14.26) — страховка от флейков.
- **`read_symbol`** (10.16) — точная навигация по Python.
- **`--auto-fix-issues`** (10.17) — цикл verify → fix → verify.
- **`--with-tests`** (10.19) — авто-тесты для изменённых файлов.
- **`--issue <file>`** (10.20) — задача из Markdown-файла.
- **Decompose + replan** (10.11.8) — v4-pro разбивает, replan
  при провале: skip/modify/stop.
- **Rollback при fail** (10.11.x) — откат успешных подзадач.

**Инфраструктура:**

- **Verify после `finish`** — pytest/ruff/mypy.
- **Бюджеты:** `--max-cost-rub`, `--decompose-max-cost-rub`.
- **Git-автокоммит** (`--commit`).
- **Безопасность** (10.15-10.18): blacklist, mask_secrets,
  `shell=False`, whitelist аргументов.

## 3. Что мешает

**Проблема 1 — планировщик разбивает «по смыслу», не «по исполнимости».**

**E7 (10.21):** задача 1.5 — `apply_plan` + `rollback`. v4-pro разбил
на 2 подзадачи, **первая = вся задача** (обе функции). Flash провалился
на `parse_error`.

**Что нужно:** планировщик должен понимать, что **две согласованные
функции в большом файле** — **сложно** для flash. Разбивать
**по функциям**, не по смыслу.

**Проблема 2 — replan получает мало контекста.**

**Сейчас:** `failed_error=loop_result.summary` (типа «max_iterations»).
**Что есть:** «не справилась».
**Что нужно:** «8 раз `read_file`, 2 `edit_file`, ошибки: `parse_error`,
`max_iterations`». **История подзадачи.**

**Проблема 3 — replan не умеет «измельчить».**

`modify` может дать **новую** подзадачу, но **такой же сложности**.
При повторном провале — **петля**.

**Проблема 4 — нет «признания сложности».**

Сейчас: `stop` после первого провала (если replan так решит). **Но**
если 3 раза подряд — **не** останавливается, **не** сообщает «задача
слишком сложная для flash».

---

**Проблема 5 — связанные правки.**

**Симптом:** задачи, где изменения в одном файле требуют
согласованного изменения в другом, **проваливаются**:

- **E17** (A.4): `checkbox` → `select`. JS + Python. **40%**, 0.81 RUB.
- **E19** (A.11): форма + `parseCommand` + `pending`.
  JS + Python + HTML. **1/4**, 16.87 RUB.

**Причина:** агент правит **локально**, не **глобально**.
Decompose **не решает** — связь между файлами сохраняется.

**Что нужно (на будущее):**

1. **Специализированные агенты** (Python, HTML, JS, CSS) —
   каждый со своим промптом. ~2 недели.
2. **Реактивный подход** — playwright: агент **видит**
   визуальный результат. ~3-4 недели.
3. **Шаблоны правок** — готовые рецепты. ~1-2 недели.
4. **Обучение по образцу** — показать пример,
   агент повторит. ~3-5 дней.

**Сейчас:** вручную / разбить на атомы
(см. `docs/tools.md` → «Когда НЕ использовать tool loop»).

## 4. Гипотезы

**H1.** **Граница flash:** ~7-10 строк goal, **1 функция**, **1 файл**.
Выше — растут флейки, `parse_error`.

**H2.** **2 согласованные функции** (например, `apply_plan` +
`rollback`) — **предел** flash. Требует **v4-pro** или **декомпозиции
по функциям**.

**H3.** **Replan с историей** (последние 5-10 шагов) — **точнее**,
чем по `summary`. Видит, **где** модель застряла.

**H4.** **Рекурсивный replan** (modify → fail → modify) — **спасает**,
если v4-pro умеет **измельчать**.

## 5. План

### Этап 1 — E8: граница flash (~20 мин)

**Что:** серия задач **нарастающей** сложности на песочнице.

**Задачи (6 штук):**
1. 1 функция, 1 правка, 3 строки goal. → mul(a, b).
2. 1 функция, 2 правки, 5 строк. → add + sub.
3. 2 функции, 2 правки, 7 строк. → mul + div с проверкой.
4. 1 функция в большом файле (500+ строк). → правка в apply.py.
5. 2 согласованные функции. → как в 1.5.
6. 3 функции, 3 правки. → набор math-функций.

**Замер:** итерации, `parse_error`, флейки, стоимость.

**Результат:** **точное правило** для `--issue` — «goal < N строк,
M функций».

**Артефакт:** `docs/experiments.md` → E8.

### Этап 2 — Улучшение replan (~2ч)

**A.** Передавать в replan **историю подзадачи** (последние 5-10 шагов):
- какие инструменты;
- ошибки;
- прогресс.

**B.** Промпт для v4-pro:
- «если `max_iterations` или много ошибок — **разбей мельче**»;
- «не повторяй формулировку, **измельчи**».

**C.** Тесты + smoke на **провале 1.5**.

**Артефакт:** CHANGELOG, тесты в `test_agent.py`.

### Этап 3 — E9: проверка на 1.5 (~15 мин)

**Что:** повторить задачу 1.5 с **улучшенным replan**.

**Замер:** справится ли flash с **более мелким** разбиением? Или
нужен v4-pro **на подзадачах**?

**Артефакт:** `docs/experiments.md` → E9.

### Этап 4 (опционально) — рекурсивный replan (~3ч)

**Что:** если `modify` даёт подзадачу, и она **снова** провалилась —
**дробить ещё раз**. Ограничение по **глубине** (2-3).

**Зачем:** Уровень 4 автономности.

**Артефакт:** CHANGELOG, тесты, E10.

### Этап 5 (после E9) — планировщик из human-goal

**Что:** пользователь даёт задачу **человеческим языком**,
агент **сам**:
1. Разбивает на подзадачи (v4-pro).
2. Показывает план.
3. Ждёт подтверждения.
4. Выполняет каждую подзадачу.
5. Адаптируется при фейле.

**✅ MVP (10.24, 2026-10-11):** `--plan` реализован —
разбиение → показ → `y/n/e` → выполнение без повторного
планирования (`run_agent_decompose(plan=...)`). E2E: `--plan`
+ `n` → 0.08 RUB, правок нет; `--plan` + `y` → 0.26 RUB,
`sub` добавлен, `3 passed`.

**Остаток:**
- **10C** `--interactive-plan` — диалог с агентом
  (через `ask_user`, направление 6 в roadmap).
- **10D** `--context-search` — агент сам ищет контекст.

**✅ Закрыто в 10.26 (2026-10-11):** `--split-goals` — одна
фраза → N issue-файлов. Полная цепочка:
`--split-goals` → `issues/*.md` → `--chain --plan` → выполнить.
E2E: 3 issues (0.19 RUB) → 3 задачи ✅ (0.77 RUB).

**✅ Закрыто в 10.25 (2026-10-11):** `--chain <dir>` — все
`issues/*.md` по очереди (`--stop-on-fail` / `--continue-on-fail`,
все планы одним `y/n/e`).

**Целевой уровень:** 4 (из 4) — «рекурсивный replan +
самоограничение + автоматическое разбиение».

**Основание:** E9 (2026-10-10) — агент работал в чужом
проекте, но пользователь разбивал вручную. Автоматизация
разбиения — следующий шаг.

**См.** `docs/roadmap.md` → направление 10.

### Этап 6 (после human-goal) — память между запусками

**Что:** состояние задачи сохраняется в
`.ai-out/<project>/tasks/<hash(goal)>/state.json`:

- `goal`, `plan`, `attempts`, `costs`, `journal_dir`;
- при повторном запуске с тем же `goal` — «продолжаем?» или
  автоматический resume (`--resume-last`).

**Зачем:** без памяти **каждый запуск — с нуля**. Это фундамент для
полной автономности: агент помнит, что делал, что узнал, где
остановился.

**Почему вынесено из «Отложено»:** раньше считалось, что одному
разработчику память не нужна (он и есть память). Для **автономной**
работы — **нужна**.

**Оценка:** ~6 ч.

**Связь:** направление 7 в `roadmap.md`.

**Артефакт:** CHANGELOG, тесты, E11 (проверка resume).

---

### Этап 7 — конвенции проекта

**Что:** `.ai-out/<project>/conventions.md` (или `.ai-coder.yaml`
в корне проекта):

- где тесты (`tests/`, `test_*.py`);
- стиль docstrings (Google / Sphinx / numpy);
- формат коммитов;
- соглашения кода (tuple vs dict, именование).

Агент **читает** конвенции **перед** задачей — как часть промпта.

**Зачем:** точнее с первого раза, меньше флейков. Сейчас агент
**каждый раз** с нуля выясняет, «как устроен проект».

**Отличие от памяти:**
- **память** — «что делали» (состояние задач);
- **конвенции** — «как устроено» (правила проекта).

**Оценка:** 1–2 дня.

**Артефакт:** CHANGELOG, тесты, E12 (проверка на проекте с
нестандартными конвенциями).

## 9. Subagents и оркестрация (10.70)

**Статус:** Router — ✅ MVP (10.70, 2026-10-15). Validator и Feedback — план.


**Основание:** E36 (2026-10-15) — `--decompose` **уже** реализует
базовую оркестрацию: разбиение, изоляция контекстов, retry, verify.

**Не строить с нуля.** **Доработать.**

### Что уже есть

- **Разбиение** — v4-pro планирует подзадачи (1 файл = 1 подзадача).
- **Изоляция** — каждая подзадача свой `_ToolLoopCtx` (своя история).
- **Retry** — при `max_iterations` → повтор через v4-pro.
- **Verify** — `pytest` после каждой подзадачи.
- **Rollback** — при `verify_failed` (откат файлов).

### Что нужно добавить

**1. Router (модель по сложности) — ✅ MVP (10.70).**

Проблема: `symbols.py` (1 функция) — flash справляется.
`tools.py` (1146 строк, связанные правки) — flash **вязнет**,
retry v4-pro — **+2-3 RUB**.

Решение (сделано): v4-pro планировщик возвращает `type` в JSON:
- **`explore`** — разведка (read-only, flash, 5 ит).
- **`edit-simple`** — правка в 1 функции (flash, 10 ит).
- **`edit-complex`** — связанные правки, файл >500 строк (v4-pro, 15 ит).
- **`verify`** — запуск тестов (flash, 3 ит).

`_resolve_subagent(st)` выбирает модель и лимит итераций.
Приоритет: явный `max_iterations` → Router → `cfg.agent.max_steps`.

**MVP хардкодит** dict в `decomposer.py`. Конфиг `agent.subagents` —
отдельная задача (TODO).

Основание: E36, E38.

**2. Validator (семантическая проверка).**

Проблема: «success» — потому что **pytest прошёл**. Header
`# (total: N symbols)` — **никто не проверил семантически**.

Решение: после подзадачи — LLM-проверка (как `--reverse-check`):
- «goal: добавить count_symbols».
- «diff: вот изменения».
- «вопрос: сделано?»

**Адаптация:** существующий `run_reverse_check` per подзадачу.

**3. Feedback loop (явная передача результатов).**

Проблема: subtask 3 **не знает**, что subtask 2 retry'нулась.

Решение: после **каждой** подзадачи — **краткий summary** (не весь
`step-N.md`) передаётся в **следующую** подзадачу **и** в планировщик
(для replan).

**4. Retry-политика.**

Уже есть: retry v4-pro при `max_iterations`.
Добавить: **retry flash** при `parse_error` (повтор), **retry v4-pro**
при `verify_failed` (с анализом ошибок).
